## 1. Two kinds of error

Doc 02 dealt with errors that **Rust** detects: when you write `v[i]`, the
compiler inserts a check "is i smaller than the length?" before the access,
and calls `panic!` if it is not.

There is another class of errors, which **Rust never even sees**, because
the one detecting them is **the CPU itself**, in the middle of executing an
instruction:

| Situation | Who detects it | What happens |
|---|---|---|
| `v[10]` on an array of 3 | Rust (a check generated by the compiler) | `panic!` → doc 02 |
| reading a memory address that does not exist | the CPU | **exception no. 14 (page fault)** |
| `div` instruction with divisor 0 (in assembly) | the CPU | **exception no. 0** |
| bytes that do not form a valid instruction | the CPU | **exception no. 6** |

A comparison with Java: a panic is like an exception thrown by your code
(`throw`). A CPU exception is like a *segmentation fault* that brings down
the whole JVM: it happens below the language.

When the CPU detects one of these problems, it **interrupts** what it was
doing and jumps to a handling routine, the **handler**. The question is:
**which** routine? The answer is in a table the kernel must provide, the
**IDT**.

Without an IDT of our own, these exceptions fall into the firmware's
handlers (which no longer work after `exit_boot_services`) or turn into a
reset.

---

## 2. What the IDT is

The **IDT** (*Interrupt Descriptor Table*) is a table with **256 lines**,
one for each **vector number** (0 to 255). Each line says:

> "When event no. N happens, jump to **this address** (the handler), using
> **this code segment** and, optionally, **this emergency stack**."

It is similar to a map of JavaScript *event listeners*: for each type of
event, the function to call. The difference is that the hardware fires the
events, and the "map" is a binary table in a format defined by Intel.

### Who uses the IDT

The 256 vectors are shared by three kinds of event:

| Kind | Source | Example | Vectors |
|---|---|---|---|
| **Exceptions** | the CPU, because of the current instruction | division by zero, page fault | 0–31 (fixed, defined by Intel) |
| **Hardware interrupts** | a device asking for attention | key pressed, timer tick | chosen by the kernel (32+) |
| **Software interrupts** | the `int N` instruction | breakpoint (`int3`), old system calls | any |

In this chapter we deal only with **exceptions**. Hardware interrupts come
in chapter 9 of the book.

### The exceptions SiliconOS handles

| Vector | Mnemonic | Name | When it happens | Pushes an error code? | Kind |
|---|---|---|---|---|---|
| 0 | #DE | *Divide Error* | integer division by zero | no | fault |
| 3 | #BP | *Breakpoint* | `int3` instruction | no | **trap** |
| 6 | #UD | *Undefined Opcode* | bytes that are not an instruction | no | fault |
| 8 | #DF | *Double Fault* | an error while handling another error | yes (always 0) | abort |
| 13 | #GP | *General Protection* | "you may not do that" (several reasons) | yes | fault |
| 14 | #PF | *Page Fault* | access to unmapped or forbidden memory | yes | fault |

The **Kind** column says what happens *after* the handler:

- **Fault**: the CPU saves the address **of the instruction that failed**.
  If the handler fixes the problem and returns, the CPU **tries the
  instruction again**. That is how on-demand virtual memory works: the page
  fault happens, the kernel loads the missing page, returns, and the
  program never notices.
- **Trap**: the CPU saves the address **of the next instruction**. On
  return, execution **continues normally**. Debugger breakpoints work this
  way.
- **Abort**: there is no way to continue; the machine's state cannot be
  trusted.

The **error code** column is crucial and comes back in section 5: some
exceptions push an extra number with details of the error, and the handler
must know that.

### And the exceptions we do not handle?

The table lines we do not fill in stay marked as "not present". If an
exception with no handler happens, the CPU cannot deliver it and raises a
**#GP** (general protection) instead, with the error code indicating which
vector was missing. Since #GP has a handler, the message shows up anyway.
That is why the #GP handler decodes the error code (section 6.4).

## 3. The format of an IDT line

Each line is 16 bytes:

```rust
#[derive(Clone, Copy)]
#[repr(C)]
struct Entrada {                     // Entrada = Entry
    endereco_0_15: u16,    // handler address, bits 0-15
    seletor: u16,          // handler's code segment: 0x08 (KERNEL_CODE)
    ist: u8,               // 0 = use the current stack; 1 to 7 = switch to IST stack n
    tipo_atributos: u8,    // 0x8E (explained below)
    endereco_16_31: u16,   // address, bits 16-31
    endereco_32_63: u32,   // address, bits 32-63
    _reservado: u32,
}

const _: () = assert!(size_of::<Entrada>() == 16);   // guaranteed at compile time
```

The handler's address comes **split into three pieces** for the same
reason as in the GDT (doc 03): the 32-bit format was extended to 64 without
moving the old fields.

`#[repr(C)]` guarantees the fields are in this exact order in memory
([rust-basico §13](rust-basico.md#13-attributes--and-)), and the `assert!`
guarantees the struct is exactly the 16 bytes the CPU expects.

### The `0x8E` byte

```
0x8E = 1000 1110
       │└┤ └──┴─ bits 0-3 = 1110 (0xE): 64-bit "interrupt gate"
       │ └────── bits 5-6 = 00: DPL 0 (only the kernel can trigger it with `int N`)
       └──────── bit 7 = 1: present
```

- **Present (P = 1):** the line is valid.
- **DPL = 0:** if an ordinary program (ring 3) tries `int 14` to fake a
  page fault, the CPU refuses with #GP. The breakpoint sometimes uses DPL 3
  so that debuggers of ordinary programs work; we do not need that now.
- **Type `0xE`, "interrupt gate":** the alternative would be `0xF`, "trap
  gate". The only difference: the *interrupt gate* **turns off hardware
  interrupts on entering** the handler, so that a timer tick does not
  interrupt the handling of an error. It is the safest choice and the one
  almost every kernel uses.

### The selector: why the GDT came first

The `seletor` field says which code segment the handler will run in, and
it must be our `0x08`. This is why doc 03 comes first: the firmware's IDT
pointed to its selector `0x38`, which does not exist in our GDT.

### Building a line

```rust
fn new(tratador: u64, ist: u16) -> Entrada {         // tratador = handler
    Entrada {
        endereco_0_15: tratador as u16,              // the low 16 bits
        seletor: gdt::KERNEL_CODE,
        ist: ist as u8,
        tipo_atributos: INTERRUPT_GATE,              // 0x8E
        endereco_16_31: (tratador >> 16) as u16,     // drop 16 bits, take the next 16
        endereco_32_63: (tratador >> 32) as u32,
        _reservado: 0,
    }
}
```

Remember [rust-basico §1](rust-basico.md#1-numeric-types-the-size-is-explicit):
converting with `as u16` **drops the high bits**. That is exactly what we
want in order to chop up the address.

## 4. What the CPU does when it receives an exception

This is the heart of the chapter. When, for example, an instruction tries
to read an invalid address, the CPU runs this sequence by itself, in
hardware:

```
 1. looks up line 14 of the IDT
 2. if the line asks for IST n: switches RSP to tss.ist[n-1]   (emergency stack)
 3. aligns RSP to a multiple of 16
 4. pushes: SS, old RSP, RFLAGS, CS, RIP                     (the "interrupt frame")
 5. if the exception has an error code: pushes the error code
 6. if the line is an "interrupt gate": turns interrupts off (IF = 0)
 7. jumps to the handler's address
```

When the handler is done, it executes the **`iretq`** instruction
(*interrupt return*), which goes the other way: it pops RIP, CS, RFLAGS,
RSP and SS all at once and returns exactly to where it was, with the state
restored. Two important details:

- **it is not `ret`**: an ordinary `ret` would pop only the return address,
  and the stack would be left misaligned;
- the error code, if any, **must be removed from the stack before
  `iretq`**, otherwise `iretq` would take the error code to be RIP.

### The frame in Rust

```rust
#[repr(C)]
pub struct QuadroInterrupcao {      // "interrupt frame"
    pub rip: u64,      // where the code was (or the next instruction, for traps)
    pub cs: u64,       // code segment of whoever was interrupted
    pub rflags: u64,   // the CPU flags at that moment
    pub rsp: u64,      // the stack of whoever was interrupted
    pub ss: u64,
}
```

The fields are in the order they sit in memory, from the lowest address
(the last pushed, RIP) to the highest (the first pushed, SS).

To print the frame with `{}` in messages, we implement the `Display` trait,
the equivalent of Java's `toString()`
([rust-basico §5](rust-basico.md#5-traits-interfaces)):

```rust
impl fmt::Display for QuadroInterrupcao {
    fn fmt(&self, f: &mut fmt::Formatter) -> fmt::Result {
        write!(f, "RIP={:#x} CS={:#x} RFLAGS={:#x} RSP={:#x} SS={:#x}",
               self.rip, self.cs, self.rflags, self.rsp, self.ss)
    }
}
```

`{:#x}` formats in hexadecimal with the `0x` prefix.

## 5. Writing handlers in Rust: `extern "x86-interrupt"`

An ordinary Rust function **does not work** as a handler, for three
reasons:

1. **It ends in `ret`**, not `iretq`.
2. **It may change registers without saving them.** In an ordinary
   function call there is an agreement (the *calling convention*): the
   caller knows some registers may be changed and saves what it needs. But
   here **nobody called**: the CPU interrupted, in the middle of some
   arbitrary instruction, code that was not expecting it. If the handler
   changes RAX, the interrupted code comes back with RAX altered and
   behaves unpredictably. The handler must save and restore **every**
   register it uses.
3. **It does not know** there is a frame and, sometimes, an error code on
   the stack.

Doing that by hand takes a piece of assembly for each handler. *Nightly*
Rust offers a shortcut: the **`x86-interrupt` calling convention**, enabled
at the top of `main.rs`:

```rust
#![feature(abi_x86_interrupt)]
```

With it, it is enough to declare the function like this:

```rust
extern "x86-interrupt" fn breakpoint(quadro: QuadroInterrupcao) { ... }
extern "x86-interrupt" fn page_fault(quadro: QuadroInterrupcao, codigo: u64) { ... }
extern "x86-interrupt" fn double_fault(quadro: QuadroInterrupcao, codigo: u64) -> ! { ... }
```

(`quadro` = *frame*, `codigo` = *code*.) The compiler generates everything:
it saves the registers used, hands over the frame as a parameter, removes
the error code from the stack and ends with `iretq`.

> **Careful: the signature must match what the CPU pushes.** If you declare
> `codigo: u64` for an exception that does **not** push an error code (or
> forget it for one that does), the handler will read the stack shifted by
> 8 bytes, and `iretq` will return to a random address. That is why the
> "Pushes an error code?" column in the table of section 2 matters so much.
> The compiler has no way to check this.

`extern "..."` in Rust specifies a function's **calling convention**: how
the parameters are passed and how it returns. You have used something
similar without noticing: when Java calls native code through JNI, there
is a specific convention for that.

## 6. The handlers, one by one

### 6.1 Building the table

```rust
static IDT: Once<[Entrada; 256]> = Once::new();

pub fn init() {
    let idt = IDT.call_once(|| {
        let mut t = [Entrada::VAZIA; 256];      // 256 "not present" lines (VAZIA = empty)
        t[DIVISAO]         = Entrada::new(divisao as *const () as u64, 0);
        t[BREAKPOINT]      = Entrada::new(breakpoint as *const () as u64, 0);
        t[OPCODE_INVALIDO] = Entrada::new(opcode_invalido as *const () as u64, 0);
        t[DOUBLE_FAULT]    = Entrada::new(double_fault as *const () as u64, gdt::IST_DOUBLE_FAULT);
        t[PROTECAO_GERAL]  = Entrada::new(protecao_geral as *const () as u64, 0);
        t[PAGE_FAULT]      = Entrada::new(page_fault as *const () as u64, 0);
        t
    });
    // ... lidt (section 7)
}
```

- `divisao as *const () as u64` converts **the function** into its
  **address**. Rust requires the intermediate step through a pointer
  (`*const ()`) to make it clear we are treating the function as an
  address.
- Only the double fault gets an IST (`gdt::IST_DOUBLE_FAULT` = 1); the
  others use the current stack (0).
- The table lives in a `Once` for the same reason as the GDT (doc 03,
  section 6): it must have a fixed address forever and is built at run
  time.

### 6.2 #BP: breakpoint, the only one that continues

```rust
extern "x86-interrupt" fn breakpoint(quadro: QuadroInterrupcao) {
    kprintln!("[excecao] BREAKPOINT (#3) em {:#x} - continuando", quadro.rip);
}
```

It prints and **returns**. Output of `./run.sh teste-breakpoint`:

```
Teste: executando int3...
[excecao] BREAKPOINT (#3) em 0x608984e - continuando
Teste: voltamos do breakpoint normalmente.
```

("Test: running int3... / [exception] BREAKPOINT (#3) at 0x608984e -
continuing / Test: we came back from the breakpoint normally.")

This test proves that **the whole path** works: the CPU saved the state,
looked up the IDT, called the handler, and `iretq` handed control back
exactly to the instruction after `int3`, with every register intact.

That is how debuggers such as GDB work: to set a breakpoint on a line, they
replace the first byte of the instruction with `0xCC`, the machine code of
`int3`.

### 6.3 #DE and #UD: simple fatal errors

```rust
extern "x86-interrupt" fn divisao(quadro: QuadroInterrupcao) {
    panic!("EXCECAO #0 DIVISAO POR ZERO\n{}", quadro);      // "EXCEPTION #0 DIVISION BY ZERO"
}
```

These errors cannot be fixed, so the handler simply calls `panic!`,
reusing all the work from doc 02 (serial, red screen, CPU halted). Output:

```
!!! KERNEL PANIC !!!
Local: src/idt.rs:131:5
Mensagem: EXCECAO #0 DIVISAO POR ZERO
RIP=0x608e546 CS=0x8 RFLAGS=0x46 RSP=0x7e96130 SS=0x10
```

**Careful when reading it:** `Local:` is the line of the `panic!` inside
`idt.rs`, not where the error happened. **The real location of the error is
`RIP`.** To translate a RIP into "file and line", we will use GDB or the
`addr2line` tool later on (chapter 10 of the book).

**Why does the division test use assembly?** In Rust, `x / 0` with integers
is checked by the compiler and becomes a panic **before** it reaches the
CPU. To see the CPU exception, we need to execute the `div` instruction
directly:

```rust
core::arch::asm!("xor edx, edx", "mov eax, 1", "xor ecx, ecx", "div ecx", ...);
//                 EDX = 0        EAX = 1       ECX = 0        EDX:EAX / ECX → divides by 0
```

#UD is tested with `ud2`, an instruction that exists precisely to be
invalid: Intel guarantees it always raises #UD.

### 6.4 #GP: general protection

It is x86's "generic" exception: the CPU uses it for dozens of "that is not
allowed" situations. The most common:

- loading an invalid selector into a segment register;
- accessing a **non-canonical address** (explained below);
- executing a privileged instruction in ring 3;
- triggering a vector with no handler in the IDT.

The **error code** helps tell them apart. When it is not zero, it
identifies the selector or vector involved, in the same selector format as
doc 03:

```
bits 3-15: index    bits 1-2: which table (00 = GDT, 01 or 11 = IDT, 10 = LDT)
```

```rust
extern "x86-interrupt" fn protecao_geral(quadro: QuadroInterrupcao, codigo: u64) {
    if codigo == 0 {
        // "EXCEPTION #13 GENERAL PROTECTION (code=0: no selector involved)"
        panic!("EXCECAO #13 PROTECAO GERAL (codigo=0: nenhum seletor envolvido)\n{}", quadro);
    }
    let origem = match (codigo >> 1) & 0b11 {        // origem = source
        0b00 => "GDT",
        0b10 => "LDT",
        _ => "IDT",
    };
    panic!("EXCECAO #13 PROTECAO GERAL (codigo={:#x}: indice {} na {})\n{}",
           codigo, codigo >> 3, origem, quadro);
}
```

**Non-canonical address.** Pointers in x86-64 are 64 bits wide, but the CPU
uses only 48 of them for addresses. The rule is that bits 48 to 63 must be
**copies of bit 47**. That splits the space into two valid halves, with a
huge forbidden "hole" in the middle:

```
0xFFFF_FFFF_FFFF_FFFF ┐
                      │ upper half (valid) ← the kernel usually lives here
0xFFFF_8000_0000_0000 ┘
                       ╳ hole: "non-canonical" addresses → #GP
0x0000_7FFF_FFFF_FFFF ┐
                      │ lower half (valid) ← ordinary programs
0x0000_0000_0000_0000 ┘
```

The `teste-gpf` test reads address `0x8000_0000_0000_0000`, which is in
the hole. The CPU does not even try to translate it: it raises #GP
straight away, with code 0 (no selector involved).

### 6.5 #PF: page fault

It happens when the CPU tries to translate an address and does not find the
corresponding page, or finds it but the access is not allowed. Address
translation (paging) is the topic of chapter 7 of the book; for now, it is
enough to know that memory is divided into 4 KiB pages and that the
firmware mapped only the part that exists.

Two pieces of information make the diagnosis precise:

- **CR2**: a control register where the CPU writes **the address that was
  being accessed**;
- **the error code**, in which each bit tells part of the story:

| Bit | If 1 | If 0 |
|---|---|---|
| 0 (P) | the page exists, but the permission was violated | the page is not mapped |
| 1 (W) | it was a write | it was a read |
| 2 (U) | it happened in user mode (ring 3) | it happened in the kernel |
| 3 (R) | a reserved bit was set in a page table (corrupted table) | — |
| 4 (I) | it was an instruction fetch (tried to execute) | — |

```rust
extern "x86-interrupt" fn page_fault(quadro: QuadroInterrupcao, codigo: u64) {
    let cr2: u64;
    unsafe { asm!("mov {}, cr2", out(reg) cr2, ...) };   // reads the culprit address
    // Messages: "executar" = execute, "escrever em" = write to, "ler" = read;
    // "pagina presente, sem permissao" = page present, no permission;
    // "pagina nao mapeada" = page not mapped; "modo usuario/kernel" = user/kernel mode.
    panic!("EXCECAO #14 PAGE FAULT ao {} {:#x} ({}, {}{})\n{}",
           if codigo & 0x10 != 0 { "executar" } else if codigo & 0x2 != 0 { "escrever em" } else { "ler" },
           cr2,
           if codigo & 0x1 != 0 { "pagina presente, sem permissao" } else { "pagina nao mapeada" },
           if codigo & 0x4 != 0 { "modo usuario" } else { "modo kernel" },
           if codigo & 0x8 != 0 { ", bit reservado na tabela" } else { "" },
           quadro);
}
```

Output of `./run.sh teste-pagefault`:

```
EXCECAO #14 PAGE FAULT ao ler 0x400000000000 (pagina nao mapeada, modo kernel)
```

("EXCEPTION #14 PAGE FAULT reading 0x400000000000 (page not mapped, kernel
mode)")

`0x4000_0000_0000` (64 TiB) is a **canonical** address (bit 47 = 0, so it
is in the lower half), but the firmware mapped nothing there. That is why it
raises #PF and not #GP.

Today the handler only reports. In chapter 7 it can become smart: if the
missing page belongs to a valid region (for example, the stack growing),
the kernel maps a new page and **returns**. The CPU repeats the
instruction, which now works, and the interrupted code never notices.

### 6.6 #DF: double fault, and the emergency stack in action

A double fault happens when **an exception occurs while the CPU is trying
to deliver another one**. It is the scenario described in doc 03, section
5.2, and the `teste-doublefault` test reproduces it on purpose:

```rust
core::arch::asm!("mov rsp, 0x400000000000", "push rax", options(noreturn));
```

- `mov rsp, 0x400000000000`: points the stack at memory that does not
  exist.
- `push rax`: tries to write to the stack.

What the CPU does:

```
 push rax → write to nonexistent memory → #PF
   └─ to deliver the #PF, the CPU must push the frame...
      onto the SAME nonexistent stack (the #PF line uses no IST) → fails again
        └─ the CPU gives up on the #PF and raises #DF
           └─ the #DF line has ist = 1:
              the CPU SWITCHES to the emergency stack BEFORE pushing
              └─ pushes the frame onto the good stack → calls the handler ✔
```

The handler:

```rust
extern "x86-interrupt" fn double_fault(quadro: QuadroInterrupcao, _codigo: u64) -> ! {
    let rsp_atual: u64;                                   // current RSP
    unsafe { asm!("mov {}, rsp", out(reg) rsp_atual, ...) };
    // "Handler running on the IST1 stack (RSP=...)"
    panic!("EXCECAO #8 DOUBLE FAULT\n{}\nTratador rodando na pilha IST1 (RSP={:#x})",
           quadro, rsp_atual);
}
```

Output:

```
Pilha IST1 (double fault): topo em 0x60ad070          ← printed at boot
...
EXCECAO #8 DOUBLE FAULT
RIP=0x608c827 CS=0x8 RFLAGS=0x6 RSP=0x400000000000 SS=0x10
Tratador rodando na pilha IST1 (RSP=0x60acf78)
```

(`Pilha IST1 ... topo em` = *IST1 stack ... top at*.)

How to read it:

- `RSP=0x400000000000` in the frame: the **destroyed** stack of whoever
  failed, exactly the value we put there;
- the handler's `RSP=0x60acf78`: 248 bytes below the top of the emergency
  stack (`0x60ad070`). **The stack switch happened.**

**The opposite proof was also done.** We temporarily changed
`gdt::IST_DOUBLE_FAULT` to `0` (no emergency stack) and ran the same test.
QEMU **closed 2 seconds after boot, with no message at all**: the last line
on the serial port was "Teste: apontando RSP..." ("Test: pointing
RSP..."). It was a **triple fault**: the #DF also tried to use the
nonexistent stack, failed, and the CPU reset. (With `-no-reboot`, QEMU
closes instead of rebooting.) After the test, the code was restored.

Two details:

- The return type `-> !` is mandatory: Intel defines that there is no way
  to resume execution after a double fault.
- Not every combination of two exceptions produces #DF, only the serious
  pairs (for example, #PF while delivering #PF, or #GP while delivering
  #GP). A #DE while delivering a #PF is handled in sequence, normally.

## 7. Loading the IDT

Same as the GDT (doc 03, section 7): the `lidt` instruction takes a
10-byte structure with the **limit** (size − 1 = 256 × 16 − 1 = **4095**)
and the table's **address**. We reuse the `gdt::PonteiroTabela` struct:

```rust
let ponteiro = gdt::PonteiroTabela {
    limite: (size_of::<[Entrada; 256]>() - 1) as u16,
    base: idt.as_ptr() as u64,
};
unsafe { asm!("lidt [{}]", in(reg) &ponteiro, ...) };
```

Unlike the GDT, nothing needs to be "reloaded": from the next exception
on, the CPU already looks up the new table.

## 8. Hardware interrupts stay off

A common question: "if `kernel_main` starts with `cli` (interrupts off),
how do exceptions work?"

- `cli` turns off only **hardware interrupts** (the IF bit).
- **Exceptions cannot be turned off**: they are a consequence of the
  current instruction, and the CPU would have no way to continue without
  handling them.

Hardware interrupts stay off until chapter 9, because we have not yet
configured the **interrupt controller** (the chip that decides which vector
each device uses). If we turned them on now, the firmware's timer could
still fire on a vector with no handler, and we would end up in #GP.

## Difference from the book

The book uses the `x86_64` crate, which has ready-made
`InterruptDescriptorTable` and `InterruptStackFrame` types. One advantage of
it: its types **prevent** you from registering a handler with the wrong
signature (with or without an error code). SiliconOS builds the table by
hand, as it did with the GDT, so **that responsibility is ours**: check the
table in section 2 before adding a new handler.

## Summary

- **Exceptions** are errors detected by the **CPU** (not by Rust). They do
  not go through the panic handler; they need the **IDT**.
- The IDT has **256 lines**. Each one points to a handler, with the code
  selector (`0x08`) and, optionally, an IST stack.
- On receiving an exception, the CPU pushes the **frame** (RIP, CS, RFLAGS,
  RSP, SS) and sometimes an **error code**; the handler returns with
  **`iretq`**.
- **`extern "x86-interrupt"`** makes the compiler generate this protocol;
  the signature must match what the CPU pushes.
- A **fault** repeats the instruction, a **trap** continues after it, an
  **abort** does not continue.
- The **double fault** uses the IST1 stack, so a destroyed stack becomes a
  message instead of a reset. This was proven both ways.

<summary><b>Review (click to see the answers)</b></summary>

1. **Why does an access to `v[10]` produce a panic, but an access to
   address `0x400000000000` produces a page fault?**
   In the first, Rust inserted a bounds check before the access. In the
   second, it is a raw pointer: there is no Rust check, and the one finding
   the problem is the CPU, when trying to translate the address.

2. **After the breakpoint handler, does execution continue at the `int3`
   instruction or at the next one? And after a fixed page fault?**
   A breakpoint is a *trap*: it continues at the next one. A page fault is
   a *fault*: the CPU repeats the instruction that failed.

3. **What would happen if the page fault handler were declared without the
   `codigo` parameter?**
   The handler would read the stack shifted by 8 bytes, and `iretq` would
   take the error code to be the return address: execution would jump to a
   random place.

4. **Why does `0x8000_0000_0000_0000` raise #GP and `0x4000_0000_0000`
   raise #PF?**
   The first is non-canonical (the high bits do not repeat bit 47); the CPU
   rejects it before translating. The second is canonical, but not mapped.

5. **In the double fault test, how do we know the IST1 stack was used?**
   The RSP read inside the handler (`0x60acf78`) is just below the top of
   IST1 reported at boot (`0x60ad070`). And, without the IST, the same test
   turns into a triple fault.
